# Changelog

it tracks, newest first. The per-system rules live in `CLAUDE.md` and each system's own `CLAUDE.md`
(`canbus/`, `lighting/`, `climate/`); the reasoning behind decisions lives in `docs/adr/`.

| 2026-10-25 | 1.20 | Repository-review fixes landed on `claude/repo-review-fixes` (tracker and rationale: `docs/reviews/2026-10-25-repo-review.md`). **R-02** (`5b53b0d`): `api: reboot_timeout: 0s` on the T-Connect Pro and Waveshare S3 RS485/CAN boards (climate controller, light controller, health monitor) and `wifi: reboot_timeout: 0s` on the dual-interface boards (T-Connect Pro, An-Penta-Plus) — the 15-minute defaults rebooted a controller whenever Home Assistant (or, for the WiFi watchdog, the access point) was away, even on healthy Ethernet; WiFi-only boards keep the WiFi default as their recovery path. **R-03** (`2aeb15e`): the HA package and ACK automation now call the light controller's real service names (`esphome.light_controller_ha_*`; the generator derives them from one `LIGHTING_DEVICE_NAME` constant instead of the pre-ADR-0015 `canbus_gateway_*`), so the readiness heartbeat reaches HA and `ha_ready` can go true; new contract test `canbus/tests/test_ha_contract.py` (in the native battery) ties `device_name`, the declared services and the HA automations together. One-time HA-side action: reload the manifest package, replace the ACK automation, delete the orphaned `canbus_gateway_*` automations. **R-04** (`ad79881`): the Home Assistant sensor tier of the room-sensor failover now goes NaN when HA is gone — `filter_out: nan` removed so `unavailable` reaches the failover, and staleness-gated `*_ha_gated` sensors return NaN after 5 min without a state-subscribed API client (pure rule in `climate/protocol/ha_tier.h`, natively tested in `test_ha_tier.cpp`, e2e in `test_room_sensors.py`). This also resolves the confidence-ledger "5 minutes" discrepancy: the 5 minutes is that HA-tier grace; the Emergency tier is NaN immediately and ESPHome's PID drives its outputs to 0 at once on NaN. **R-01 / R-01b** (`1472a90`, `ed4d157`): PID heat/cool outputs are no longer wired to the same actuator (ESPHome's PID routes by sign, not mode, so the valve was driven with |error|); each direction is a template output gated on `hp_mode` (`climate/protocol/pid_direction.h`: HEAT → heat only, COOL → cool only, SANITARY_ONLY → neither) for radiant valves, fancoils and floor mixing valves, so a below-dew-point supply now closes the mixing valve. Fancoils take a required `fancoil_role` (`boost`, `cool_only`, `heat_cool`): boost fancoils are started only by the boost coordinator (the `{zone}_boost_enabled` bypass is closed) and the sottotetto (`heat_cool`) now actually heats. Circulation-pump demand follows the gated actuation (`pid_direction::actuating()`), not PID intent. Native test `test_pid_direction.cpp` and e2e `test_radiant_direction.py` added. Autotune caveats documented: tune in the loop's season, halve gains on dual-output loops (real swing 0..1), set boost fancoils to COOL by hand first. **R-10 partial** (`bf1aa11`): the fancoil-boost e2e (`test_fancoil_boost.py`) now runs in CI on `main` and in the battery, its harness joins the `esphome config` gate, and `conftest.py` fails fast when the harness API port is already taken. **R-11 docs** (this entry): version header fixed, changelog moved here from `CLAUDE.md`, failover/PID-tuning/ledger docs corrected to match the code. Compile and hardware bring-up of the above are still owed (PlatformIO was unreachable in the review environment) | AI Assistant |
