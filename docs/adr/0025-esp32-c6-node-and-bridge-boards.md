# ADR-0025: ESP32-C6 boards from `hardware/`: the nodo 503 wall node and the dual-TWAI bridge

## Status

**Accepted** (2026-11-04). Root-tree ADR (spans `boards/`, `canbus/` composition and the
`registry/` profile enum). Amends ADR-0017's choice of preferred bridge board only.

## Context

`hardware/` (imported from `afmotta/can-bus-node`) holds two PCBs generated by script:

- **`hardware/nodo503/`**: a wall-button node for an Italian 503 box. ESP32-C6, one TJA1051T/3,
  six button inputs, 24 V from the bus.
- **`hardware/bridge/`**: a two-channel CAN bridge on the same chip, 56 × 36 mm, with the
  120 Ω terminations on a DIP switch.

Until now their firmware lived outside the registry: a hand-written
`hardware/nodo503/firmware/nodo503.yaml` (Wi-Fi + Home Assistant bring-up) and a draft board
file for the bridge. The ESP32-C6 has two TWAI controllers, and ESPHome 2026.8.0 gives each
`esp32_can` entry the next controller in declaration order, so both sides of the bridge are
interrupt-driven with driver queues. The T-2CAN's zone side is a polled MCP2515 with two RX
buffers, which can drop frames before they are enqueued, invisibly.

## Decision

1. **Two new board files**, `boards/esp32-c6-nodo503.yaml` (can0 on GPIO23/22) and
   `boards/bridge-c6-twai.yaml` (can0 = backbone GPIO23/22, can1 = zone GPIO20/19). The order of the two
   `esp32_can` entries in the bridge board is load-bearing and is commented as such.
2. **Two new registry profiles** in `PROFILES`, no schema change:
   - `buttons-c6`: `esp32-c6-nodo503.yaml` + `buttons_6_c6.yaml` + `tx_watchdog.yaml`.
   - `bridge-c6`: `bridge-c6-twai.yaml` + `bridge.yaml` + `tx_watchdog.yaml`.
3. **`tx_watchdog` on both.** Every ESP32 TWAI transmitter needs it (R-17): ESPHome never calls
   `twai_initiate_recovery()`, so a bus-off node stays off until rebooted.
4. **`buttons_6_c6.yaml`**: six inputs on GPIO7/0/1 (J3, buttons 1–3) and GPIO20/19/18 (J4,
   buttons 4–6), reusing `button.yaml`, 0-based like `buttons_8.yaml`. A test pins the GPIO list.
5. **`bridge-c6` is the preferred bridge**; `bridge-t2can` stays as the second source. The
   single-purpose rule of ADR-0005 is unchanged: `bridge-c6` carries no buttons and no sensor kit.
6. **Radios off on both boards**, as on every other node (ADR-0005): no `wifi:`, `api:`, `ota:`.
   Flashing and logs go over the native USB on J5, which is not fitted by default.
   The Wi-Fi/Home Assistant bring-up firmware stays in `hardware/nodo503/firmware/` for bench
   boards; the PCB does support Wi-Fi/OTA, and enabling it on wall nodes would be a separate decision
   against the "dumb, frozen nodes" principle.
7. **No registry rows are added by this ADR.** Node ids are allocated when a physical board is
   commissioned (`node_id_hwm` is monotonic); the profiles only make that possible.

## Consequences

- A C6 wall node or bridge is added with the normal registry flow (`allocate_node.py`, profile
  `buttons-c6` / `bridge-c6`, then `generate_nodes.py`); nothing in `canbus/nodes/` changes today.
- Two compile fixtures (`canbus/tests/compile_bridge_c6.yaml`, `compile_buttons_c6.yaml`) join CI
  and the verification battery.
- The nodo 503 has the Qwiic port but no I²C is declared: no C6 profile carries the sensor kit.
  A `buttons+sensors-c6` profile would be a new row and its own decision.
- The PCB sources stay outside CI; only the firmware they imply is gated.

## Not verified

- `esphome config` passes on both fixtures (2026.8.0). `esphome compile` and the behaviour on real
  hardware (two TWAI controllers on one chip, bus-off recovery, the button inputs on J3/J4) are not
  verified; the bridge in particular has not been powered.
